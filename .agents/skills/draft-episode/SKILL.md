# draft-episode

## 全季初稿先行

新项目默认 `drafting.mode: full_season_review`；用户要求“全部出完再统一修改”时，一次完成计划内全部集数。先运行 `./run.sh next <项目路径>` 并检查来源、计划和实际前情。明确授权的全季初稿不受旧的两集预览上限限制；媒体、付费生成、正式交付及批准记录不在文字授权范围内。

可按集并行写作。前集尚未完成时，只把计划的 reveal/withhold 用作暂定信息边界，标记依赖待补。收齐后用 `recap update-working` 按实际稿件登记前情并逐集语义复核，再运行 `recap check` 和 `recap context <项目路径> <末集号加一>`。不得只更新指纹代替内容核对。

文案阶段顺序为：全季初稿与编辑包 → 用户统一修改/反馈 → 导入差异、另存新版并复核 → 文案确认。初稿完成前不催用户先改第一集；文案确认之后才按当前授权进入媒体，保留既有定稿版本。

读取 [写稿与标记](../../../docs/WORKFLOW.md#写稿与标记)，再按需读取本集原文、计划、口播 / 题材 / 人设规范。只允许写本集目录的任务卡子会话改用 `python -m bookflow next <项目路径> --read-only --json`，不刷新共享进度。用派生的 `state.json`、`episodes/recap.yaml` 和 `feedback/rules.yaml` 确认版本。

剧情类读取 [剧情文字总纲](../../../style/narrative_charter.md)、[共享写法](../../../style/story_craft.md) 和本书已有的 `writing_direction.md`。解释服从当前场景与读者已知，不把内部全剧透简报当口播顺序。

每次写稿前运行 `./run.sh lessons context <项目路径>`。先通过 learn-feedback 处理待归类的真实改稿；应用有证据的 active_rules，候选不作强制要求。事实规则回到原文核对。在本次写作记录中列出采用的规则编号及具体例子；没有反馈时保持未校准状态。参见 [改稿导入与反馈流程](../import-feedback/SKILL.md)。

1. 用 `./run.sh recap context <项目路径> <集号>` 读取已复核的前序实际内容；缺失时按上节临时并行规则处理。旧书先按统一前情表的迁移流程核对，不建立第二套账本。
2. 剧情类内部提纲先写叙事节拍与依据，再核对哪些场景承载 takeaway；不要求每个过渡段交付一个结论。论述型作品按核心问题、论证链与必要解释组织。剧情类的人物感受、处境与环境是叙事的一部分，以原文为据或明确表为解读；在动作与矛盾中展开，避免按人物结局提前裁判。文学性调整按全季统一基准规划，不用抒情替代案件信息。
   先铺清人物、对象和动作，再进入感受或解释，避免无前文锚点的“她”“那里”“这意味着什么”。场景可以停在动作、迟疑或未解问题上，无须追加总结回收。听众尚未理解事实时，先补具体前提，不用抽象感慨代替。
   修订稿必须替换原段落，不得把“补细节”“加长”写成同一事件的第二遍复述。每段先判断信息是否已经交付；已经交付的句子要合并、改写或删除。
   检查模板回归：同一集内“没有回答，只……”“屋里只剩下……”“先看见 A，再看见 B”各最多出现一次；如果动作已经完成，直接进入下一件事。人物听觉标签在本集第一次出场使用一次，同一场戏随后只用名字；隔了较长场景再出现时才重新标记，标签可以换成刚发生的具体动作。
3. 保留历史，另存 `draft_vN.md`，自查口语和去 AI 腔；口播年份中的 0 写“零”，不要写“〇”，并检查全稿没有让配音误读的“〇”。再运行 `lint`、`quotes` 并核对事实。独立听感检查默认不启用，不能为补报告在同一上下文假装盲审。

用 `./run.sh edit copy <draft> --output <human_edit目录>` 为每集建立编辑包；全季全部生成后统一交给用户。返回稿件用 `./run.sh edit import <改稿路径> --baseline <编辑基线路径>` 导入，阅读差异、另存新版并检查。第一集包含在同一轮改稿中；看到初稿或要求继续不等于文案确认。

剧情类用具体场景、关系与必要推理呈现深度；承载它们的实际口播可以使读者理解处境，无须另念观点总结。论述型作品核对命题、条件与推理的实际交付。隐藏提纲和标记不算交付收获。原型预览继续完成已授权工作，但不伪造前序有效账本。

人物显示名以本书 `analysis/characters.yaml` 为准，原文名和人物 ID 用于身份核对。写稿前运行 `./run.sh names-check <项目路径>`；旧称未同步时先按[名称同步参考](../import-feedback/references/name-consistency.md)处理。不要把另一书目的同名人物规则带入本书。

声音在写稿阶段同步规划：需要进入故事的声音写成制作标记 `[音效：描述｜类别｜功能｜位置]`，例如 `[音效：远处海港汽笛｜ambience｜bed｜本段开头]`。该标记只作规划注记，不会成为口播，也不会自动生成正式 cue。定稿候选稳定后，重新生成句子表并核对锚点，再逐条把仍然采用的标记转录到 `episodes/epNN/production/sound_cues.yaml`：补齐 `cue_id`、`sound_class`、`function`、句子 ID/文本锚点、原文依据或制作氛围、`gap_policy`、时长和状态。该 YAML 是检查、估算和生成的唯一清单；删除或调整稿件标记时同步复核对应 cue。当前 `sound cues` 命令只初始化/迁移清单，不会从稿件自动提取标记，手工转录后再运行 `sound check` 和 `sound estimate`。不要使用尚未被稿件解析器支持的 `[环境]` 或 `[关键]` 标记。声音类别和功能必须有原文依据，旁白已经念出拟声词时不重复配同类声音；开头黄金 5 秒不放可辨认事件音、撞击、铃声或系列标识，方案明确时可安排极轻、低于旁白的连续底层。
