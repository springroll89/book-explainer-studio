# 口播视频声音制作规范

本规范适用于书籍精讲的“纯口播＋声音设计”阶段。它把口播、事件音、环境底和混音拆开，避免音效生成、时间轴和字幕互相污染。

## 1. 责任边界

- **豆包 2.0**：只生成当前版本的纯口播。输入是干净的口播正文，不放 `[音效]`、模型参数、时间码或制作说明。
- **豆包 1.0**：生成有辨识度的事件音、过程音、环境声、回声和系列片头。它与 2.0 共用本机 API 配置，但调用和素材分别记录。
- **本地脚本**：可以合成极轻且均匀的底噪，例如空调、住宅家电和荧光灯底层；也负责裁切点缀、循环、交叉淡化、插入停顿和生成审计表。
- **ChatCut**：只负责导入、剪辑、混音、字幕、画面和导出，不负责调用豆包生成模型。

## 2. 从稿件到最终音频

### A. 规划标记与正式 cue 清单

1. 写稿时可用 `[音效：描述｜类别｜功能｜位置]` 留下声音构想。这是作者的规划标记，不进入口播；不要使用解析器不支持的 `[环境]`、`[关键]` 标记。
2. 稿件版本稳定后重新生成句子表，逐条核对标记对应的句子 ID 和正文锚点，并人工把采用的标记转录到 `production/sound_cues.yaml`。至少填写 cue ID、类别、功能、句子锚点、原文证据或制作氛围、`gap_policy`、时长、停顿策略和状态。未采用的构想不进入清单。
3. `./run.sh sound cues <episode>` 当前只初始化/迁移清单，不解析 Markdown 内联标记。运行初始化后应确认 YAML 中确有预期条目；缺项时先人工补齐，再运行 `sound check` 和 `sound estimate`。YAML 是机器检查、估算和后续制作的唯一清单。
4. 读取项目状态、当前稿件、声音清单和前序依赖；运行 `./run.sh guard <项目> voice-generate --ep N` 和 `sound-generate`。
5. 生成纯口播前，年份中的数字 0 写作“零”，不要使用“〇”（U+3007）；豆包曾将“〇”压缩成极短音，导致读音和词级时间戳异常。记录稿件哈希。稿件一旦改变，旧口播、字幕和依赖它的时间轴全部视为待重做。用当前 Markdown 生成纯口播文本；导出文本只保留正文和正常标点。

另交付人工审阅版 `audio_script_vN.md`：保留已定稿全文，在对应正文锚点处标注音效声源、叙事作用和按语速估算的落点。与之配套的 `sound_cues.yaml` 是唯一机器清单；`voiceover.txt` 只含干净正文。规划落点不等于实际时间码，最终落点以混音后的时间表为准。

### B. 生成并验收口播

1. 用豆包 2.0 提交纯口播，查询到任务完成后保存原始音频和返回的句子/词级时间戳 JSON。
2. 每集提交前读取项目级 `production/voice_cast.yaml` 并锁定批次中的 revision 与 SHA-256；旁白音色须与 `project.yaml` 一致。提交后的 job JSON 要和锁定音色表比对 `speaker`、`resource_id`、模型和采样率。任何不一致都不能进入混音。多会话同步规则见 `docs/WORKFLOW.md` 的 O14。
3. 不用 ASR 文本替代稿件。ASR 或模型返回的时间戳只用于对齐、发现漏字、合并句和审计。
4. 检查返回文本长度、句子数、最后一个词的结束时间和音频可解码性。服务可能把相邻短句合并，例如“她拨丈夫的电话。”和“关机。”，必须用词级时间重新切开。

### C. 设计与生成声音素材

每条声音至少写明：

- `cue_id`、小节、句子 ID 或正文锚点；
- `sound_class`：`ambience`、`event`、`process`、`design`、`music`；
- `function`：`bed`、`story_event`、`hook`、`reveal`、`transition`、`mood`、`motif`；
- 直接给模型的描述、目标时长、复用键、原文依据或“制作氛围”；
- `sync_mode`：`blocking`（事件音让出口播）、`bed`（环境底铺在下方）、`punctuation`（句边界点缀）；
- 口播动作、前后留白、压低多少分贝、是否循环、是否可选和当前状态。

声音存在的理由是让听众更清楚地知道**谁在什么地方做了什么**，或让关键转折和情绪落点更有记忆点。听不出声源、不能说明叙事作用的泛泛白噪，不进入成片。

正式执行时，项目的 `production/sound_cues.yaml` 是机器检查的规范入口。Markdown 稿件标记用于保留写稿时的声音想法；必须在句子 ID 稳定后人工转录到 YAML，不能假设命令会自动提取。若当前提案尚未迁移到 YAML，先完成转录和 `sound check`，不能让旧 YAML、旧时间线或旧 ChatCut 模板代替当前提案。

### D. 低成本生成策略

1. 默认每条素材只生成 **1 个版本、调用 API 1 次**。版本数就是 API 调用次数；需要重做必须明确记录原因，不自动追加版本。
2. 均匀环境声生成 12–20 秒短循环，要求首尾平稳、没有突出的事件。使用时随机起点，首尾交叉淡化 0.5–1 秒；噪声型底层可做极轻微（约 ±2%）变速，海浪和人群不做明显变速。
3. 零散事件不要塞进底层。一次生成一段包含多个彼此隔开的点缀，再由脚本切成单条，在不规则时间点播放；同一场景同一事件不超过三次。
4. 空调、家电、灯管等极轻均匀底层先试听本地合成版本。可接受就不调用 1.0，保留生成方法和文件哈希。
5. 若平台存在单次最低计费时长，把 1–5 秒点缀合并到一次调用后再切开；不能为了省钱把同一长环境声拆成多次独立生成。
6. 估算费用时按“实际计费规则”计算。若按分钟计费，成本约为 `计费秒数 ÷ 60 × 单价`；请求时长只是目标，模型返回可能更长，实际扣费以平台账单为准。

### E. 事件音与环境底的时间逻辑

- 敲门、电话铃、关门、货梯停靠、绳索受力、火焰突然窜起等会改变动作先后，使用 `blocking`：口播断句 → 留白 → 音效完整播放 → 留白 → 口播继续。同一时刻只保留一个前景声音。
- 雨声、风声、海浪、房间底噪等使用 `bed`：与口播并行，通常比口播低约 20–28 dB；即使压低也要听出场景特征。
- 过程音（脚步、倒酒、车辆驶过）可用 `partial_gap`：让最有辨识度的 1–2 秒露出，其余部分压在口播下。
- 事件若落在一句话中间，优先在稿件中改成两个可对齐短句，或使用返回的词级时间在边界切开；不要把音效硬压在正在说的字上。
- 开场前 5 秒不放可辨认的事件音、撞击、铃声或系列标识，给旁白建立注意力。若声音方案明确需要极轻的连续铺底（如 C01），可以低于旁白约 18 dB 进入，但不能抢注意力、制造突然响声或占用黄金句前的停顿。

### F. 拼接、混音和时间表

1. 先把阻断事件插入口播，形成“口播＋停顿”的新轨道；再按实际起点叠加底层和点缀，最后导出唯一时间表。
2. 事件素材按计划时长裁切，超出部分不能悄悄改变口播锚点；所有插入的前后留白、复用和裁切记录在 timeline JSON。
3. 参考混音：环境底比旁白低 25–15 dB，过程音低 18–12 dB，事件音不超过旁白 0 dB；成品目标约 `-16 至 -14 LUFS`，真峰值不高于 `-1 dBTP`。最终以手机外放和耳机试听为准。
4. C01 等铺底在事件音开始前淡出，事件结束后再恢复；句间点缀同时压低底层。可选片尾音（如 C25）只有在确认成本和节奏都值得时加入。
5. 画面分段、字幕对齐和转场都使用这份最终“口播＋音效”时间表，不能继续按纯口播时长推算。

### 音频版本绑定

重新混音、调整事件音留白或更换口播后，旧版时间表、字幕、镜头切点和视频模板全部失效。视频必须以当前混音文件及其配套的 `timing_actual` 为唯一时间基准，重新切分画面、重新生成字幕并核对末端时间；禁止只替换音频文件而沿用旧时间轴。交付前用 `ffprobe` 对比音频与视频总时长、字幕最后一条时间和最后镜头结束时间，四者不一致时不得交付。

### 声音标识与集名标题卡

当系列声音标识（例如 C04）本身已经让旁白停下时，可以在该声音段内叠加本集集数和集名。标题卡与声音段共用同一时间范围，不增加停顿、不另起字幕条，也不遮挡需要解释剧情的画面；使用清晰的简体中文确定性排版。标题文字取自分集计划或本集 package，声音版本或停顿变化后必须重新核对标题卡落点。

标题卡与字幕的季播基线记录在项目 `production/video_style_baseline_v1.yaml`：标题卡使用“第 N 集—细分隔线—两行集名”的居中布局；字幕使用简体中文、最终稿标点、底部居中、白字黑描边。除集数、集名和实际时间范围外，后续各集沿用同一视觉参数。

### 开场钩子连续性

开场前两句或前一完整钩子必须连续讲完，再进入系列声音标识或其他阻断音效。第一句与第二句之间不得连续堆叠多个 `gap` 事件；杯子、门、脚步等非核心点缀改为低音量 `duck`，或移到后续语义段。开场通常只保留一次必要的系列标识停顿，并与标题卡共用该时间段。

## 3. 生成和验收命令顺序

```bash
./run.sh guard <项目> sound-generate --ep N
./run.sh sound cues <集目录>
./run.sh sound check <集目录>
./run.sh sound estimate <集目录>
# 用户确认费用后，才调用豆包 2.0 / 1.0
./.venv/bin/python tools/doubao_long_tts.py ...
./.venv/bin/python tools/doubao_audio_gen.py ...
./run.sh timing import <集目录> --audio <口播音频>
./run.sh sound assemble <集目录>
./run.sh sound mix <集目录>
./run.sh sound check <集目录>
```

当前 `bookflow/sound.py` 负责清单检查、估算和本地结构化拼装；实际豆包调用脚本是单独的生成层。项目若有针对当前声音清单的专用混音脚本，必须把输入稿件、时间轴来源、输出路径和验证命令写入制作记录，不能把旧时间线冒充新版本。

## 4. 必做验收

- 音频能完整解码，`ffprobe` 的时长、采样率、声道和文件路径正确；FFmpeg 空输出检查通过。
- 事件音在对应段落可辨认，压低后仍能听出声源；没有遮字、抢戏、突然爆音、无人声要求却出现人声/音乐/警报，或新增原文事实。
- 阻断事件确实让口播停下并恢复，停顿没有切断语义；底层循环没有明显接缝或固定重复。
- 输出 `timeline.json`，至少记录原始口播时长、加入停顿后的时长、每个事件的绝对起点和时长、复用/跳过项、稿件哈希和输出路径。
- 音频更换后重新生成字幕。字幕文字来自最终稿的简体中文和标点，ASR 只做词级时间和差异审计。
- 先听整集，再抽查开头、中段、结尾及每类声音至少一处；用户听感确认前状态只能写 `preview_awaiting_human`。

## 5. 从声音进入画面和成片

1. 声音混音和时间表验收通过后，才判断哪些段落需要新画面；不能先按纯口播估算镜头。
2. 依据最终时间表和语义完整段落生成分镜。每幅静态图通常停留 8–15 秒，画面必须解释当前口播中的人物、地点、动作、物件或线索；每个生成资产在一集内只出现一次。人物图严格使用已确认的定妆参考，手机屏幕、时间和文字等不可控细节宁可留空。
3. 画面完成后统一使用一种简单的平移转场（默认 `builtin:tr-soft-wipe`），不混用慢淡入、推拉等效果；抽查交界前、中、后三个画面和开头 30 秒的变化密度。
4. 字幕从最终稿生成简体中文和标点，用实际混音时间表对齐；ASR 只做词级时间和差异审计。口播或混音变化后，字幕必须重新生成。
5. ChatCut 只负责导入已生成的口播/音效、剪辑、混音、字幕、画面、转场和导出。第一集先做样片并经用户 AV1 确认，之后剩余集数可按每批约两集分给不同会话；每集必须先有已接受的声音时间表，图片确认后再合成成片。

## 6. 第一集已验证的完整制作闭环

第一集的实际顺序是：最终 Markdown 口播稿 → 豆包 2.0 纯口播 → 豆包 1.0 事件音与环境底 → 阻断事件插入停顿 → 循环与本地底噪合成 → 混音和最终时间表 → 按语义切分画面 → 严格使用人物定妆图生成剧情图 → ChatCut 统一平移转场与字幕 → 本地成片试听和抽查。任何一步更换稿件或音频，都要从新的时间表重新对齐后续步骤。

这次制作留下的操作经验：

- API 返回时长可能偏离目标时长，且可能合并相邻句子；最终时间轴要以实际词级时间和成品音频为准。
- 每条音效默认只生成一个版本、调用一次；均匀底层用 12–20 秒短循环，零散事件单独切片；能用本地脚本合成的极轻底噪不调用付费模型。
- 事件音让出口播：先断句、留白、播放音效、再留白；环境底才与旁白并行。开头黄金 5 秒不放可辨认事件音或系列标识。
- 旧口播、旧 SRT、旧时间线和旧 ChatCut 模板不能通过改名继续使用；必须按稿件哈希和实际输入重新生成并验收。
- 字幕文字始终来自最终稿，ASR 只用于时间对齐和错漏审计。音频变更后必须重建字幕。
- 口播音色是系列级锁定参数；若误选音色，即使音效、时间轴和字幕都正确，也必须废弃该集口播并重新合成、重新导入时间戳、重新混音和重建字幕。

## 7. 连续无口播留白检查

系列片头、关键揭示等声音链可以暂时让旁白停下，但不能机械叠加多个音效的等待和事件时长。混音后核对“上一句结束 → 下一句开始”的连续无口播区间；除有明确叙事理由外，不应超过 8 秒。优先缩短等待或合并音效链，不新增没有原文依据的旁白。
