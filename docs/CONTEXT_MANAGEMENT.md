# 上下文管理与跨聊天续接

本工作室是一个文件驱动的混合工作流。聊天窗口负责当前一轮的理解、判断和协调；项目文件负责长期保存事实、版本、反馈和审校状态。重要结论不能只留在聊天记录里。

## 四个组成部分

| 组成 | 位置 | 作用 |
|---|---|---|
| 工作方法 | `.agents/skills/`、`docs/`、`roles/` | 规定每个阶段读什么、做什么、如何交付 |
| 确定性程序 | `bookflow/`、`run.sh` | 读取、分段、比较、校验、计算指纹和导出 |
| 持久资料 | `projects/<book>/` | 保存原文、分析、分集稿、反馈、审校和账本 |
| 当前协调 | Codex / Claude Code 聊天 | 结合资料做写作、解释和取舍，不替代项目资料 |

这不是后台持续训练系统。人工改稿会被保存为差异和风格规则；后续写稿通过读取这些文件来应用规则。

## 项目隔离

- 一本书使用一个 `projects/<book>/` 目录，不能把人物、译名或风格规则静默带入另一部书。
- 每集保留 `draft_vN.md`，改稿、审校和导出另存版本；不覆盖历史稿。
- 原文导入批次不可变。事实、引用和审校报告绑定 `source_generation` 与稿件哈希。
- `status.yaml` 记录当前阶段和待办；`episodes/working_continuity.yaml` 记录实际前序内容与依赖；`feedback/rules.yaml` 记录已生效及候选风格规则。
- 正式确认仍需人工 G4 和有效系列账本。预览状态不能写成已批准。

## 最小读取范围

开始新一轮工作时，先读：

1. 项目 `status.yaml`；
2. `episodes/working_continuity.yaml`；
3. `feedback/rules.yaml`（或运行 `./run.sh feedback-context <项目路径>`）；
4. 当前任务涉及的计划、本集稿件和审校报告。

同时读取 `project.yaml` 的 `drafting.mode`。`full_season_review` 表示先写完全部文案、再统一人工改稿；不要根据旧 G2/G3 状态恢复为逐集停顿。并行初稿可暂按计划信息边界写作，缺失前序条目须标记待补；整季汇总前从各集实际文本补录工作连续性并核对衔接。原有的定稿账本和批准状态保持真实。

按任务缩小范围：

- 写第 N 集：本集计划、有效前情账本或连续性文件、相关原文笔记和当前风格规则。
- 全季风格调整：先读取全季计划、当前风格规则和各集实际版本，再按集建立增强版；不要只改一集后把局部语气当成全季规则。
- 导入人工改稿：编辑基线、改后 DOCX、差异文件和必要的原文证据。
- 事实审校：当前稿、对应原文段落和前序依赖，不加载无关集数全文。
- listener 审校：只提供纯口播句子和受众信息，不提供聊天历史、提纲或其他角色结论。
- 配音或制作：读取纯口播、声音清单和本集音效卡，不重新加载整本原文。

不要为了“保持记忆”把整本原文、所有历史稿和全部审校报告复制进一个聊天。需要更大范围时，先生成摘要并说明用途。

## 阶段检查点

每个阶段完成后，在项目文件中留下可续接的结果：

- 导入：原文批次、格式、提取质量和抽查结论；
- 分析：简报、人物、线索、覆盖审计和未决项；
- 规划：分集计划、核心收获、揭示 / 保留边界；
- 写稿：稿件版本、采用的风格规则和来源标记；
- 审校：三方原始报告、汇总、哈希和未解决问题；
- 人工修改：基线、差异、事实核对、学习记录和受影响下游；
- 交付：输出路径、版本、渲染检查和仍需人工确认的事项。

## 聊天过长时如何续接

可以直接开启新聊天，不需要记文件名。只要说：

> 继续这个项目，接着做：……

如果同时有多本书，再说：

> 继续《书名》这个项目，接着做：……

由代理自行读取项目状态、连续性、风格规则和本轮需要的资料。新聊天应先做状态核对，不凭旧聊天记忆声称已完成。若上游稿件有新改动，先检查依赖和名称一致性，再继续下游写作或打包。

## 可选的当前工作包

项目较大时，可以在项目根目录生成一个短的 `CURRENT_CONTEXT.md`，只包含当前版本、前情摘要、风格规则、待办和本轮文件清单。它是导航摘要，不是新的事实来源；具体事实仍以原文、稿件和审校报告为准。更新工作包不能替代更新状态、连续性文件或账本。
