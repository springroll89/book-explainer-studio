## 工作模式与确认

- **全季文案先行（新项目默认）**：`drafting.mode: full_season_review`。日常由 `next` 推进方案，再完成全季初稿与编辑包、统一改稿和文案确认。用户明确授权文字先行时，不用首集定调或两集预览上限阻断后续文字；来源、计划和实际前情仍检查。媒体、付费、正式交付不在文字授权内。
- **书目档位**：剧情默认 `profile: story`，科普、非虚构、历史默认 `explainer`，旧书未声明时仍按精讲检查。剧情可不列核心 takeaway、不强制钩子；精讲保留核心收获层级。两档必做事实核对，独立听感和去 AI 腔默认关闭、按需开启，真实听感在样片中验收。

- **开发 / 原型演示**：继续已授权的实现、样稿和检查，用 `export --preview` 交付并列出未完成人工节点，不伪造确认。
- **正式生产**：使用方案、文案、画风、定妆、声音、样片、成片各项确认；不另设首集文字风格关卡。声音按集确认（首集沿用旧成品时由样片覆盖），批量阶段每两集先确认声音再做画面。已有同范围授权有效，但“继续开发”不是内容批准。
- **状态如实表达**：`preview` 表示预览产物；`partial` 表示检查或必要工作未完成；`awaiting_human` 表示已有可审结果，等待指定人工动作。机器检查通过不等于内容和听感已验收。
- **确认绑定对象**：记录用户确认的具体稿件版本和指纹。改动后重新评估受影响范围，不能把旧确认套给新稿。

新文案确认在本机日志保存纯口播快照，用于 `next` 显示首处文字差异；旧日志缺快照时只报告文件和哈希，不能猜测具体改动。用户本人基于已确认稿修改、经 `edit import` 导入并完成语义复核后，若原稿、改稿报告与当前 `final.md` 的纯口播均匹配，普通 `next` 可追加带轮次和文件哈希的文案确认“沿用”记录。导入文件不自动证明编辑者身份；助手必须核对实际稿件来源。`next --read-only` 不追加记录；撤回、未复核、证据失效或文字不匹配时仍需重新确认。沿用只解决文案确认，不替代教训分诊、前情复核或音画重检；其他来源和其他确认项的自动沿用仍未实现。

文案变动导致媒体输入指纹不一致时，`next` 与 `进度.md` 会按依赖图列出本集受影响的已完成阶段。正式媒体只读清单、链接哈希及定稿/句子表等小文件，不读取或哈希音视频大文件；隔离 selftest 夹具仍会核验测试产物。重跑由 `produce` 按依赖顺序核验，配音按段落缓存复用未变化部分；已归档的集先按清单取回。不会仅因集号靠后就把所有后续集列为待复核；确实依赖变更前情的集数由 recap 指纹检查单独识别。

用户在聊天里明确要求具体字词替换时，助手改完定稿后运行 `./run.sh edit instruction <项目> <集号> --quote '<用户原话>' --replace '<改前>' '<改后>'`；每处替换重复一个 `--replace`。程序将原话、原确认指纹、来源版本和精确替换写入本地 `feedback/instructions/`。普通 `next` 只有在现稿与替换结果完全一致、原话来源有效且证据未变时，才追加“沿用”。可读到本机会话时，登记原话须与最近一条用户消息逐字一致；读取失败按警告记录，不阻塞。撤回、额外改动、整集替换和含糊替换均不能自动沿用，需重新确认。

助手主动小改先登记精确替换和语义风险核查：`./run.sh edit assistant-change <项目> <集号> --replace '<改前>' '<改后>' --risk-review '<理由>' --no-identity-change --no-plot-fact-change --no-ending-change`。默认阈值 `approvals.minor_change_ratio: 0.03`。只有旧确认、来源和证据有效且无其他变化时，文案确认保持通过，待过目项在下次人工确认展示，不因此阻塞制作；这不产生新的人工作出批准记录。超阈值、整体替换、风险不明或证据失效仍需确认。前情语义复核和媒体哈希检查照常执行，旧音视频不因小改而被视为有效。

## 剧情类文字取向

剧情作品使用 [剧情文字总纲](../style/narrative_charter.md) 与 [共享手艺](../style/story_craft.md)，沿信息揭示顺序探索冲突和处境；风格在全季改稿中校准。内部全剧透资料供核证，不能直接用作口播顺序。

## 上下文管理与跨聊天续接

本工作室是文件驱动的混合工作流：Skill 和文档规定方法，`bookflow/` 与 `run.sh` 执行确定性检查，`projects/<slug>/` 保存长期资料，聊天窗口只负责当前一轮协调。它没有依赖聊天记录的后台训练；人工反馈通过差异和规则文件在后续写稿时重新加载。

一本书一个项目目录，每集保留版本链。先运行 `./run.sh next <项目路径>`，以项目文件推导状态；聊天历史不替代稿件、连续性、反馈和审校证据。按当前阶段 Skill 读取必要材料，不预加载整本原文和全部历史稿。

聊天过长时可以新开聊天。用户只需说“继续这个项目，接着做：……”；由代理自行读取上述状态入口和当前任务涉及的计划、稿件与报告。新聊天不得凭旧对话声称已完成；上游改动时仍须按账本和依赖规则复查下游。

## 风格校准与反馈

涉及人名更正时，按[名称同步参考](../.agents/skills/import-feedback/references/name-consistency.md)处理稳定人物 ID、现用名和旧称，并同步活动资料、新稿与派生文件。

人工改稿已接入原稿快照、差异和批注导入，以及写稿前风格上下文加载。具体操作见[改稿导入与反馈流程](../.agents/skills/import-feedback/SKILL.md)。首次使用先交付编辑稿；真实改稿返回后再学习，不能预先填入虚构偏好。

首次没有参考稿时可用 [默认讲述者](../style/voices/default.md) 做未校准预览。不能把代理自选示例当成用户认可风格。

有用户指定参考后，分别记录：句长与节奏的统计画像；开场、解释、评论、收尾的人工阅读画像；用户明确喜欢和不喜欢的部分。参考原件只作本地分析，不整段复制到可公开样本中。量化阈值是候选，不能照抄一份样稿设成通用硬门槛。

反馈记录“位置 / 原句 / 用户为什么改 / 改后 / 适用范围”。例如：用户把“值得注意的是，他并非不愿意”改为“他其实愿意，只是当时走不开”，可形成“这类转折先说清行动条件”的局部候选；不能直接推导出全局禁止所有对照句。

可计数的本书规则放在 `feedback/lint_rules.yaml`，`rules` 列表沿用 `style/banned.yaml` 的 `id/level/max/patterns`。每条必须写 `origin_ep`；不写 `applies_to` 时只检查这一集。扩大到多个集号时显式写列表或 `{from: 1, to: 3}` 并附 `scope_evidence` 用户原话；`applies_to: all` 只用于原话明确说“全季 / 所有 / 以后”等的情形。格式或范围不合法时 lint 报错，不把单集意见静默推广。

用户已经要求修改某条规则时直接执行并验证。只要求评估、或从一次样例推导跨项目偏好时，先交付具体差异建议，标为候选，待认可后扩大范围。已确认稿件因反馈改动时，按账本依赖规则处理。

## 原文入库与版本

先确认指定文件的格式与可提取内容。首版命令支持范围以 `ingest --help` 为准；需转换的 EPUB、MOBI、PDF 等应在副本上处理，保留原件、版本、译者和转换记录。没有可靠提取文本时先标明阻塞，不能按书名凭记忆拆书。

入库生成不可变批次；`source/current.json` 指向当前批次。其 `paragraphs.jsonl` 保存全书段落，`chapters.json` 保存章节索引。全书唯一 ID 使用 `p00001` 形式；后续证据必须同时绑定当前 `source_generation`，不能把旧批次的同名编号当作当前依据。

抽查开头、中段、结尾及章节交界，确认文字无漏页、乱序、严重 OCR 或编码错误，目录、版权页和正文边界正确。机器能分章不代表分章正确。

## 三类证据

详细原则见 [忠实度与深度](../style/fidelity.md)。

| 内容 | 内部写法 | 审校要求 |
|---|---|---|
| 书中事实 / 改述 | `〔据 p00001-p00003〕` | 当前原文及上下文支持这项主张 |
| 原文短引 | `〔引 p00001〕「原句」` | 引号内逐字核对；版本一致 |
| 剧情场景对白还原 | `“中文对白”〔据 p00001〕` | 同段有原文依据；核对场景意思，不冒充逐字短引 |
| 外部事实 | 稿件 `〔外 E01〕`；结构化依据 `ext:E01` | 已登记并实际核实来源 |
| 自己的解读 | 段首 `〔延伸〕`，附相关证据 | 口播可听见“我的理解是”等表态 |

外部事实登记到 `analysis/external_sources.yaml`：

```yaml
sources:
  - id: E01
    title: 实际核查的来源标题
    url: https://example.org/replace-with-verified-source
    accessed_at: 'YYYY-MM-DD'
    status: pending
    claim: 该来源具体支持哪一条主张
    published_at: null
```

以上是结构说明，示例 URL 不可作为证据。读过实际来源并核实对应主张后才设 `status: verified`，`accessed_at` 填实际核验日期；发布日期可查时另记。来源不支持结论时，即使登记为 verified，也要修正或删除引用。暂时查不到的内容放待核清单，不能出现在定稿的确定性断言里。此工作流默认不调用付费接口。

## 拆书与覆盖审计

1. 用 [chapter-reader](../roles/chapter-reader.md) 按章精读；可在不共享写入目标的情况下并行。每条事实带依据，单列第 2、3 层素材与不确定处。
2. 统筹写 `analysis/book_brief.md`、`threads.yaml`、`characters.yaml`、`misreadings.md`。作者意图需要依据；重点解释这本书值得精讲什么。
3. 在拆书阶段运行 `./run.sh check projects/<slug>`，生成 **`analysis/coverage_machine.json`**。它只列确定性错误、候选和统计信号；旧 `coverage` 命令暂保留用于单项排查。
4. [coverage-auditor](../roles/coverage-auditor.md) 打开原文逐条判断，写 **`analysis/coverage_review.yaml`**。保留判断理由、依据和未决事项，记录对应原文批次及机器报告指纹。
5. 补分析后重跑机器检查，再确认旧判断是否适用；语义复核与机器结果分别保存。完成后依 `next` 准备分集及方案确认材料。

高频词只提供候选。审计还要抽查低频但关键的转折、作者自述与缺乏深度素材的章节。机器错误清零不代表书被完整读懂。代理撰写的覆盖判断报告也不等于用户已人工确认。

## 分集与深度

剧情类先辨认原作叙事单元、冲突推进、视角与信息揭示，在自然节点规划分集，再写 `core_question`；`story` 档位的 `takeaways` 可留空，只作策划参考，不先设道德观点再裁剪情节举证。论述型作品仍先梳理核心问题与论证。写出的目标都须具体、有据，避免只写“理解人性”“获得启发”。

```yaml
episodes:
  - ep: 1
    covers: [ch01]
    genre_mode: suspense
    target_chars: 3000
    core_question: 本集要回答的具体问题
    takeaways:
      - id: K1
        layer: 2
        core: true
        text: 本集必须讲清的具体认识
        evidence: [p00001]
```

这只是字段片段；`story` 可省略 `target_chars` 和 `takeaways`，但仍须标题、原文覆盖、剧透边界等。以 `check-plan` 的实际检查结果补齐。未覆盖的章节在 `skipped` 说明取舍，不能静默漏掉。

四层深度分别是：发生了什么、为什么、作者怎么写或论证、如何评价与应用。`explainer` 档位的每集和系列必覆盖层由项目配置决定；`story` 不作层级硬检查。**个人延伸比例不等于深度：**解释原书论证可以很深入而几乎没有个人评论；大量感慨也可能没有交付任何核心收获。

剧情类的第 2、3 层可在动作、关系与信息变化中交付；审稿时应能指出承载它们的句子与依据，不要求另加总结段。第 4 层不作默认目标。具体口径见 [忠实度与深度](../style/fidelity.md)。

当前阶段检查命令：`./run.sh check projects/<slug>`；`check-plan` 保留用于单项排查。按 `next` 处理方案，已明确授权的全季文字工作可继续，计划错误仍须修复。同版同范围已有确认不重复索要。

## 写稿与标记

写作前运行 `./run.sh next projects/<slug>`，再用 `./run.sh recap context projects/<slug> N` 读取前序实际稿件。计划不是已经讲出的内容，定稿与工作稿的依据不可混用。

全季可并行初写：前集未齐时按计划暂写，标记前情待补；收齐后用 `recap update-working` 记录实际正文，并逐集复核揭示、身份与时序。运行 `recap check` 后再交全季编辑包，指纹一致不能代替语义复核。

可用 `./run.sh jobs plan projects/<slug> --stage draft` 建立全季初稿卡，再用 `./run.sh jobs run projects/<slug> --stage draft` 串行启动独立 Codex 会话。每张卡先过写稿守卫，旧版初稿不得覆盖；父执行器只在新稿通过集号、lint、quotes 后建立本集 Markdown 编辑包。队列卡完成只表示单集机器检查通过，尚须按全部实际文本补录工作连续性并做语义复核，再交付全季编辑包。该自动入口还没有真实 Codex 端到端验收，不应直接用于不可恢复的现有稿件。

每集用 `edit copy` 建立独立编辑基线，全季交齐后统一反馈，不要求先改首集才写余下文案；改后复核再提交文案确认。

装载项目配置、本集计划、账本汇总、相关分析与原文，以及 [口播规范](../style/spoken_rules.md)、对应 [题材规范](../style/genres/) 与项目人设。剧情类另读文字总纲与本书已有的 `writing_direction.md`，先写场景节拍和依据，再核对哪些段落承载 takeaway；不要求每个过渡段交付一个观点。论述型作品按核心问题、论证链和必要解释组织提纲。

人物感受、环境与关系是剧情叙事本身，应随有依据的场景展开。用户提出文学性增强时，默认按**全季统一调整**处理，除非明确指定单集。先建立统一基准，再逐集另存新版；保持事实、人物身份、线索顺序、剧透边界和前后集依赖，不把单集的特殊语气扩大为全季硬规则。

剧情类先铺清人物、对象和动作，再进入感受或解释，避免听众猜测指代。场景可以停在动作、迟疑与未解的问题上，不要求简短总结或情绪回收；解释在补足必要理解后回到故事。审校时检查“听众是否需要猜这句话在说谁 / 什么”，也检查评论是否截断了此刻的紧张与感受。论述型作品按论证需要解释概念和前提，不强求转成场景。

稿件标记：

- 段首 `〔延伸〕` 作用到下一个空行。该标记用于统计与审校；正文仍须明确表达解读立场。
- `[钩子]` 放在触发句末；有标记只表示作者打算在此吸引人。
- `〔线索 T01 埋〕` / `〔线索 T01 收〕` 记录线索动作。
- `[画面：…]`、`[BGM：…]`、`[音效：…]`、`[字幕：…]`、`[镜头：…]`、`[备注：…]` 是会从纯口播剥离的制作信息。声音构想使用 `[音效：描述｜类别｜功能｜位置]`；不要使用解析器不支持的 `[环境]` 或 `[关键]`。
- `## 小节` 与 HTML 注释只供制作和审校，不作为观众已听到的信息。

每轮另存 `draft_vN.md`。引用、事实依据、延伸与制作标记在纯口播中去除，所承载的正文保留。句子 ID 由当前稿件解析生成，如 `s001`；改稿后须重新生成、重新绑定，不能把旧 ID 套到新文本。

声音构想可在稿件里用 `[音效：描述｜类别｜功能｜位置]` 做规划标记；它们会从纯口播中剥离。稿件稳定并重新生成句子 ID 后，人工把采用的构想转录到本集 `production/sound_cues.yaml`，绑定句子 ID/正文锚点，补齐类别、功能、原文依据或制作氛围、避让策略、时长和状态。当前 `sound cues` 命令只初始化/迁移清单，不自动读取 Markdown 标记；转录完成后再运行 `sound check` 和 `sound estimate`。YAML 是后续生成和混音的唯一正式清单。豆包 2.0 只接收纯口播并生成连续旁白；豆包 1.0 负责环境声、拟音、回声和可复用片头。不得用音效补写原文没有的事实或线索。口播改动后，只复核受影响的声音条目。

事件音和环境音的时间逻辑不同：人物敲门、关门、枪响、电话铃、快门等会改变听众对动作先后的判断，默认在触发句或触发词的边界切开口播，先留出短暂停顿，播放拟音，再恢复口播；具体停顿由声音时长和语速估算，不把音效硬压在正在说的字上。雨声、风声、房间底噪等 `bed` 声音可以与口播并行，但要自动压低，不能遮住字。若事件发生在一个句子中间，优先把句子拆成两个可对齐片段，或改写为两个短句后重新合成；不依赖模型自行“猜”出停顿。

### 音效辨识度与叙事验收

音效是口播从合格走向优秀的重要细节，但不是每个场景都要强行配音效。每条声音必须回答两个问题：听众能否从声源辨认出正在发生什么，以及它是否让剧情信息、空间关系或情绪转折更清楚。只有连续底噪、无法辨认来源的“氛围”不能作为合格成品；即使是 `bed` 环境声，也要保留至少一个可识别的声源或动作层。

优先把辨识度高的声音配置在关键剧情转折、线索揭示、人物状态变化和结尾悬念处。提示词应写具体声源、先后顺序、强弱和收束方式，并明确排除“普通白噪”“泛泛环境音”等结果。例如机场场景应有广播提示、飞机轰鸣或其他可确认机场的声音；工地场景应有钢索绷紧、金属敲击等具体声源，具体选择仍须服从正文依据。

生成后必须实际试听验收，至少检查：能否说出主要声源；放在对应口播段落是否增强理解或情绪；压低音量后是否仍保留辨识度；是否遮字、抢戏或新增原文没有的事实。任一项不通过，就标记为待重做，优先重写提示词再生成，不以“已经有一个音效文件”视为完成。音效存在的理由是叙事价值，而不是完成数量。

## 独立审校与通过条件

先运行 `lint`、`quotes` 与计划检查，定位硬错误，再让 [fact-checker](../roles/fact-checker.md) 核对原文事实与人物身份。两个档位默认都不单设听感和去 AI 腔审校，口语与文风并入写稿自查。需要时显式开启 `review.listener_enabled: true` 或 `review.deai_enabled: true`，再按 [listener](../roles/listener.md) / [deai-editor](../roles/deai-editor.md) 执行。已提交的可选报告仍完整核验，不能借默认关闭忽略其中问题。精讲的核心收获检查不变。

### 按需启用 listener 时的隔离

统筹运行 `./run.sh listener-input <稿件路径>`。导出的输入只包含 `audience` 和类似 `[s001 0:00] 纯口播。` 的内容，没有书名背景、计划、takeaways、提纲、钩子标记或自评。

使用真正独立、未继承写稿历史的子代理（例如支持时以 `fork_turns: none` 新建），给它角色指令与最小输入，禁止读取项目其他文件或联网补背景。不支持独立上下文时，保留自查但将独立听感审校标为 `partial / awaiting_human`。同一上下文改扮 listener 不能算盲审。

报告中的 `engaged` / `dropoff` 每条必须有 `sentence_id`、`trigger` 原句和 `why`。统筹以句子 ID 与原句精确核对钩子，区分标记的钩子、实际触发的句子和自然吸引点。**不能用相近估算秒数认定钩子兑现。** 时间码只作制作估算，真实听感仍需试听。

### 汇总与阻断

独立报告保存后再汇总。每份报告顶层绑定 `draft_sha256`、`source_generation`、`dependency_hashes`（首集为 `{}`）。全季文字草稿绑定有效工作连续性中的前集实际哈希；`final.md` 或 `status: final` 仍绑定前集定稿哈希。listener 只处理纯口播，统筹在收到独立回答后封装这些版本元数据。

- fact 报告包含 `core_takeaways: [{id, delivered, supported}]` 和 `findings`。
- deai 报告包含 `findings`。
- listener 报告包含 `listener: {engaged, dropoff, takeaway}`；每个反应按上节保留触发原句。
- 汇总还包含 `reviewers`，如 `fact: {status: completed, independent: true, report: 'review/fact_v1.yaml'}`，另外两角色同理。报告路径相对本集目录；仅在实际完成且独立时如实填写。
- `findings` 每项包括 `id/severity/category/message/resolved`。严重性采用 `P0/P1/P2`，类别按实际问题填写。

角色没有运行、只审了一部分或输入已污染，要按实记录。原始报告未解决的 P0 或深度问题不能在汇总里悄悄标为已解决；修订后需要针对新稿的复核。结构字段以 `review-check --help` 和当前模板为准。

- 核心 takeaway 的 `delivered` 和 `supported` 都要为真，并能指向实际口播和依据。
- **核心收获未讲、讲错、缺依据，是必修项。即便被标作 P1，也不受“P1 最多三条”豁免。**
- 事实错误、错误引用、歪曲作者、剧透、前后矛盾和未完成的必要审校，不得靠平均评分通过。
- 非阻断问题按事实、听得懂、深度、吸引力、文字美感的顺序处理。warning 是诊断，不能为了消灭提示把稿子改僵。
- 到最大审校轮数，只表示需要人工选择或补资料；不能自动通过。优先局部修改，并在改稿后重跑受影响检查。

阶段检查命令：`./run.sh check <项目路径>`；旧 `review-check <稿件路径> --report <汇总路径>` 暂保留用于指定报告的单项排查。正式生产先保存带最终元数据的 `final.md` 候选，再针对该文件审校；改 front matter 也会改变指纹，不能把旧 draft 审校直接盖到新文件上。预览可审 draft，并保留真实待办状态。

## 统一前情表与依赖

统一前情表记录 **当前草稿实际说了什么**，并在有效文案确认后保存 **`final.md` 的定稿快照**：已揭示事实与身份、线索埋收、未解决问题和可用回顾。隐藏提纲、删掉的草稿、未来计划都不能冒充实际前情。语义复核必须由读过当前稿件的人员明确完成，机器指纹不代替内容判断。

候选绑定稿件 SHA-256、原文批次及前序依赖。可通过以下命令检查或提取已复核的上下文：

```bash
./run.sh recap check projects/<slug>
./run.sh recap context projects/<slug> 2
```

文案确认后按当前定稿保存快照，不再单独盖章入旧账本：

```bash
./run.sh recap snapshot-final projects/<slug> 1
```

若定稿纯口播与已复核工作稿不同，必须先按实际定稿填写 `--actual <内容.yaml>` 并重新语义复核。旧书目未迁移 recap 时暂保留 `ledger` 兼容命令，不可用它代填或绕过有效人工确认。

前集定稿变化时，前情快照过期；曾依赖旧版本的后续集数进入待复核。**前集重新确认、重新保存快照，不会自动清除后集对旧指纹的依赖。** 必须逐集比较受影响事实、回顾、剧透与线索，修订或确认无影响后，以新的实际复核记录更新依赖。未完成复核时不输出有效后续上下文，不正式打包。

## 打包与真实验收

预览：`./run.sh export <稿件路径> --preview --review <汇总路径>`；没有汇总也能预览，但会明确显示审校未完成。正式导出：`./run.sh export <定稿路径> --deliver --review <汇总路径>`，必须满足本轮审校、有效前情定稿快照、有效文案确认与成片确认（含字幕及合规文件）。旧 G4/RELEASE 闸门不再作为正式导出的依据。

交付内容包括纯配音稿、独立的画面与声音清单、质检摘要，以及标题、封面文字、重点词、简介标签和配音提示等发布文案。未实现自动生成的部分由代理补全，并写清检查范围。

声音规划与纯口播分离：稿件内的 `[音效：…]` 是写作阶段的构想标记；重新生成句子 ID 后，将采用项人工转录到独立的 `production/sound_cues.yaml`，再运行声音检查和估算。当前 `sound cues` 命令不提取稿件标记。豆包 2.0 只生成 `voiceover.txt` 对应的口播音频；豆包 1.0 生成 cue 表中的音效、环境声、回声和可复用片头。每条至少写小节、句子 ID / 正文锚点、按语速估算的出现时间和声音内容，并标明 `gap_policy`、目标时长、复用键、叙事目的及原文依据或制作氛围。事件音须写明口播停顿和恢复动作；环境音写明压低音量策略；句间点缀只放在句边界。不要把制作指令留在纯口播里，也不要用音效新增原文没有的事实。

验收纯口播没有内部标记、证据号、标题注释或残留制作指令；制作清单中的时间注明“按语速估算”。质检摘要记录：稿件和原文版本、检查结果、每条核心收获与依据、独立审校是否完成、账本依赖是否有效、确认状态和剩余问题。

标题、封面和简介同样遵守事实与剧透边界。没有实际生成音频、试听、字幕文件或视频时，不声称已完成这些交付。流程默认止于本地文件；付费模型只有在完成制作预检、成本估算并得到用户明确确认后，才按声音清单调用。

## 阶段守卫与画面节奏

### O13 声音设计与混音（硬规则）

声音制作使用 `production/sound_cues.yaml` 作为唯一清单；历史 `sound_plan.yaml` 只保留作迁移依据。每条声音同时记录 `sound_class`（`ambience`、`event`、`process`、`design`、`music`）和 `function`（`bed`、`story_event`、`hook`、`reveal`、`transition`、`mood`、`motif`）。现实逻辑决定声音如何发生，叙事功能决定它如何与旁白排列；同一时刻只保留一个前景声音。

默认避让规则：环境底和音乐用 `duck`；点状事件在故事事件、钩子或揭示处用 `gap`；过程音用 `partial_gap`；设计音在揭示或钩子处用 `gap`。`gap` 必须计算前后留白，单个通常不超过 3 秒；过程音只让 1–2 秒峰值露出。硬规则是开头黄金 5 秒不放可辨认的事件音、撞击、铃声或系列标识；方案明确时可放极轻连续底层，但必须低于旁白且不能制造突然响声。故事世界音效要有原文依据，旁白已经念出拟声词时不得重复放同类音效。

声音按清单驱动：稿件稳定后核对句子锚点，人工转录采用项，再执行 `sound check`、`sound estimate`、有效媒体阶段与本地混音。`sound cues` 不会自动提取稿件标记。付费生成须先过制作预检、费用上限和用户授权；豆包 2.0 配音与豆包音频 1.0 音效已接入，真实服务端/账单仍待首批验收。具体步骤见 [produce-audio](../.agents/skills/produce-audio/SKILL.md) 与其媒体清单参考。


### O14 多会话批量制作与音色同步

正常流程在首集声音制作前确定旁白与全季对白人物的音色对照；全季定稿后先标注说话人、汇总缺口，由用户决定新音色并集中写入共享音色表。已开工书目的音色补齐属于迁移补救，不作为新项目的默认顺序。

首集样片获用户确认后，后续集数按不重叠的集号每两集新建一个制作会话；末批不足两集时处理剩余集数。每个会话在自己的批次内完成语音、音效、混音、字幕、分镜、图片与视频合成及核对，避免媒体素材在单个会话堆积占满上下文。各会话只写自己批次和集号目录，不改共享音色表。已定稿的口播正文按确认版本和 SHA-256 读取；不重开已接受的改稿意见，不为声音规划擅自改写正文。只有用户明确要求改稿，或发现阻断制作的具体问题时，才提出局部修改。

每集先交付三份互相绑定的材料：干净的 `voiceover.txt`；供人审阅的 `audio_script_vN.md`（保留全文，并把每个拟用音效放在对应句子锚点旁，标注声源、叙事作用和按语速估算的落点）；机器使用的 `production/sound_cues.yaml`。音效落点是规划位置，最终时间以配音、音效混音后的实际时间表为准。不得把音效标记或制作说明混进纯口播。

跨会话人物音色以本书 `production/voice_cast.yaml` 为唯一来源。按 `analysis/characters.yaml` 的稳定人物 ID 查找：已有映射直接沿用；主要说话人物须有独立确认音色；次要人物可用已确认的共用音色池。批次中若发现此前遗漏的说话人，先暂停相关付费生成，在批次目录提交 `voice_requests_epNN.yaml`；旁白转述不自动产生角色配音需求。协调会话按 ID 去重，只向用户询问一次，并负责更新共享音色表及 `revision`，批次会话随后重新锁定版本。

每个批次清单复制音色表的 `revision` 和 SHA-256。先汇总音色请求，再锁定同一版音色表开始付费 TTS；生成过程中不更换版本。锁定前若有更新，重读并更新指纹；锁定后若指纹不一致，暂停 TTS，不沿用旧音色。

批次阶段依次为：核对已定稿件及其指纹（文案已确认的集数不重提；如仍待确认，不重开编辑审稿，而是在批次材料中附上现稿及指纹供用户确认）→ 核对已确定的音色表 → 音效规划与带落点音效稿 → 用户集中确认待确认稿件与声音方案 → 锁定音色版本并在费用预估与用户授权后生成口播/音效 → 混音和用户试听确认 → 按最终音频时间表制作分镜与图片 → 用户确认画面 → 成片合成与核对。新发现的音色缺口按上段退回协调会话处理，不在批次制作中擅改共享表。声音或画面确认只绑定当前批次记录的稿件、音色、音频和分镜指纹。

音频版本绑定：重新混音、调整停顿或更换口播后，旧版 `timing_actual`、字幕和分镜切点不得继续使用。视频必须以当前混音文件随附的最终时间表重新切分和对齐，并在交付前用 `ffprobe` 核对音频、视频、字幕末端和最后镜头的时长一致。

若系列声音标识段包含独立停顿，可在该时间段叠加本集集数与集名标题卡。标题卡复用现有停顿，不延长音频、不重复字幕，文字来自分集计划或本集 package，并与声音版本和最终时间表绑定。

季播视频样式固定：标题卡使用“第 N 集—细分隔线—两行集名”的居中层级；字幕使用简体中文、保留最终稿标点、底部居中、白字黑描边。具体参数以项目 `production/video_style_baseline_v1.yaml` 为准，后续集只替换集数、集名和实际时间范围。

开场钩子连续性：前两句或前一完整钩子必须连续讲完，再进入系列声音标识或其他阻断音效；不得在句间连续堆叠多个 `gap` 事件。非核心点缀改为 `duck` 或移到后续语义段，开场只保留一次必要的系列标识停顿。

混音起始参考：环境底相对旁白 -25 至 -15 dB，过程音 -18 至 -12 dB，事件音不超过旁白 0 dB；旁白关键频段 1–4 kHz 要留出空间；成品积分响度 -16 至 -14 LUFS，真峰值不高于 -1 dBTP。最终音量、停顿和音效数量以第一集样片的手机外放与耳机试听为准。

写稿、声音规划、画面制作和外部生成前运行 `./run.sh next <项目>`，媒体制作另运行 `./run.sh produce check <项目> epNN`。人工确认由用户在聊天里作出；阶段状态见 [flow.py](../bookflow/flow.py)，确认有效性和交付物绑定见 [approvals.py](../bookflow/approvals.py)。句子表使用 `./run.sh sentences generate`，锚点用 `./run.sh anchors check`，配音时间用 `./run.sh timing import`。静态图项目先运行 `./run.sh pacing budget`，分镜完成后运行 `./run.sh pacing check`，样片确认后才建立基线。字幕必须使用当前最终口播稿的简体文本和标点；ASR 只用于取得词级时间、时间对齐与差异审计。音频或稿件版本变化会使旧 SRT 失效，必须重新生成并记录新稿件哈希、时间轴来源、字幕条数和视频时长。若 ASR 合并了相邻句子，允许按词级时间拆分，但字幕文字仍以最终稿为准。导出前要验证字幕覆盖到实际口播、没有超出音频总时长，并在开头、中段、结尾实际打开渲染帧检查简体、标点、错别字和可读性；只有字幕文件存在而视频中不可见，不能算字幕完成。

静态图的时长边界、跨集隔离、人物上下文绑定、唯一画面和音画相关性，以 [visual-development Skill](../.agents/skills/visual-development/SKILL.md) 为唯一制作规则。分镜先满足语义完整和已核实的人物身份，再运行 `pacing check`；机器通过后仍须人工看实际画面。本工作流总览不另设时长例外或镜头数量目标。

静态图连续播放时，在本地 FFmpeg 中统一使用简单平移转场（默认 `slideleft`，时长以项目配置为准）；禁止慢慢淡入和多种效果混用。转场不改变口播节奏，不遮挡字幕和关键物件，且必须抽查交界前、中、后三个实际画面，并核对整集画面资产零重复。

### 系列片头海报

系列片头海报与剧情分镜分开制作。先依据实体书封面和全书剧情意象生成不含文字的 16:9 背景，再用本地确定性排版叠加系列文案、中文工作名、德语原名和作者名；准确文字不交给生图模型生成。标题应使用笔画均匀、字重足够的字体，优先通过浅色填充、轻微深色描边或偏移阴影提升可读性，不用大块不透明底板破坏背景构图。每次改字从干净背景重新渲染，保留独立 `poster_vN.png` 与元数据 JSON。输出需验证 3840×2160（或项目指定 4K 尺寸），并查看缩小预览，检查缺字、细笔画消失、裁切、主体遮挡和“贴片”感。
